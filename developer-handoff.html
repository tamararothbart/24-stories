1. What This Product Is

24 Stories is a premium subscription service. A storyteller (typically an elderly family member) receives 26 weekly prompts over 6 months. They record or type their story each week via tell.html. Tamara (the founder) edits each story by hand. The edited story is emailed to the subscriber's family each week. At the end, all 26 stories are printed in a hardcover book and delivered.

Price: R6,795 once-off, upfront via PayFast. Book included. Extra copies R1,200 each.

The product runs on: a static website (Netlify), Airtable as the database, Make.com as the automation layer, Mailjet for email delivery, Cloudinary for media storage, and Claude API + OpenAI Whisper for voice transcription and text cleanup.

5. The Immediate Problem and Its Solution

Scenario 1 Stage 2 must be rebuilt from scratch. The current tested build ends at the Router (emails 2 and 3). Make's Router is a terminal point — modules cannot be appended after it without a full rebuild. Scenario 2 (Week 1 Prompt) was never built.

The problem

Email-4 (Week 1 Prompt) must fire after email-1 (welcome letter) is sent — not based on PayFast activation. The subscriber must receive their welcome email before their first prompt. The original design used Airtable Watch Records as the Scenario 2 trigger — this was confirmed broken in this project. A scheduled trigger has a race condition: Make sets Status=Active at the start of Scenario 1 Stage 2 (before emails are sent), so a scheduled Scenario 2 could fire before email-1 is delivered.

The solution — no Airtable schema changes required

Step 1 — do this first
In Make, create a new scenario. Add a Custom Webhook trigger module. Name it "Scenario 2 — Week 1 Prompt". Copy the webhook URL Make generates. Record it in make-build-log.html before doing anything else.
Step 2 — complete Scenario 2 modules
After the webhook trigger, build these modules in sequence:

Webhook receives: StorytellerEmail, StorytellerFirstName, StoryHelperEmail, LibraryToken (passed from Scenario 1 Stage 2 HTTP call).

2a. Airtable Search Records [Subscribers] — filter: LibraryToken = {{LibraryToken from webhook}} — retrieves full subscriber record for Airtable Update at end.
2b. Airtable Search Records [Prompts] — filter: Week = 1. Do NOT use the Formula field — use Make's native filter module. Leave Formula field empty.
2c. Mailjet — Send email-4 → StorytellerEmail. (Content from make-email-content.html.)
2d. Filter on connector: StoryHelperEmail is not empty → Mailjet — Send email-4 → StoryHelperEmail.
2e. Airtable Update Record [Subscribers] — set PromptNumber = 1, LastPromptSentDate = today. Use the Subscriber record ID from step 2a.
Step 3 — rebuild Scenario 1 Stage 2
Rebuild this scenario from scratch. The module chain is identical to the tested version, with one addition after Mailjet email-1:

Webhook → Filter (payment_status = COMPLETE) → Airtable Update Record [Status=Active, SubscriptionStartDate, PromptNumber=0, LibraryToken=custom_str1] → Airtable Get Record → Airtable Create Record [Payments] → Mailjet email-1 (Storyteller) → HTTP > Make a request [POST to Scenario 2 webhook URL, body: StorytellerEmail, StorytellerFirstName, StoryHelperEmail, LibraryToken] → Router → Route A: GiftGiverEmail not empty → email-2 / Route B: StoryHelperEmail not empty → email-3.

⚠ The webhook trigger module must use the same URL as the existing tested scenario:
https://hook.eu1.make.com/63gxymbozbgic8v4qtvjzn9nkruo3g8k
To preserve this URL: open the existing Scenario 1 Stage 2, note the webhook name, create the new scenario using the same webhook connection — or rebuild in place by deleting modules from right to left and rebuilding. Do not delete the webhook itself.
Step 4 — test end-to-end
Using Hoppscotch (hoppscotch.io):
1. POST a test subscriber payload to Scenario 1 Stage 1 webhook → get back a record_id.
2. POST a PayFast COMPLETE payload to Scenario 1 Stage 2 webhook with that record_id as custom_str1.
3. Confirm in Mailjet logs: email-1 sent, then email-4 sent in sequence.
4. Confirm in Airtable: Status=Active, PromptNumber=1, LastPromptSentDate set.
5. Delete test records from Airtable (Subscribers and Payments tables).

See make_build_protocol.md for exact Hoppscotch test payloads.

6. Hard Constraints — Do Not Violate

  • Do not add fields to Airtable. Any schema change (new field, renamed field, changed type) breaks Make module field mappings across every scenario. Get Airtable right before touching Make. The schema is locked at v3.2 — see airtable-setup-guide.html.
  • Do not use Airtable Watch Records as a Make trigger. Confirmed broken in this project. Use scheduled trigger + Search Records, or webhook-triggered.
  • Do not use the Formula field in Airtable Search Records in Make. Make's variable system intercepts curly braces and breaks every formula. Leave the Formula field empty. Use Make's native filter module placed after the Search Records module instead.
  • Preserve the Stage 2 webhook URL. It is registered in the PayFast merchant dashboard as the notify_url. Do not delete this scenario or generate a new webhook for it.
  • All automated emails send from stories@24stories.co.za. Never hello@. hello@ is Tamara's manual address only — never in Make.
  • Filter StoryHelperEmail not empty before every Story Helper Mailjet module in every scenario. Global rule — no exceptions.
  • Do not insert modules between existing modules in Make. Make does not support this. To change the middle of a chain, rebuild the scenario from scratch.
  • Iterator Array field: click the field → variable picker opens → select "Airtable — Search Records (bundle)" at the very TOP of the picker. Do not select individual field badges.
  • Variables in Mailjet email body: must be inserted via the variable picker (blue badges). Do not type {{variable}} manually — it will not resolve.
  • Tell.html cleanup uses claude-sonnet-4-6. Do not downgrade to Haiku. Quality matters here.
  • Test via Hoppscotch, not tell.html. Make must be in Run Once mode (listening) before clicking Send in Hoppscotch.
