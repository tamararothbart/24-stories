Build Rules — read at the start of every session

  1. One scenario per session. Build it completely, test it, record the webhook URL and flags, then close.
  2. Never move to the next scenario until the current one is confirmed working.
  3. Record every webhook URL the moment Make generates it — paste it into this log before doing anything else.
  4. Never fill in modules between established modules during build. Give every module in order, no gaps.
  5. Read this log in full at the start of every session before opening Make.
  6. At the end of every session: update this log, commit to GitHub, write the next session trigger.
  7. If a session starts compacting, stop at the end of the current scenario — never mid-scenario.
  8. Cross-scenario dependencies (webhook URLs, field values) are flagged below and must be verified before the dependent scenario begins.

2026-04-16 — Architecture review session. No new scenarios built.
Full diagnostic of why Scenario 2 was being skipped.

Findings:
1. Scenario 2 was never built — build log correctly showed "To Do".
2. Scenario 1 Stage 2 confirmed module chain: Webhook → Airtable Update → Airtable Get → Airtable Create [Payments] → Mailjet email-1 → Router → Route A: email-2 (Gift Giver) / Route B: email-3 (Story Helper). Email-4 is NOT in this chain.
3. Airtable Watch Records trigger was attempted for Scenario 2 in a prior session and confirmed broken for this project. Do not use again.
4. Scheduled trigger (every 15 min, filter Status=Active AND PromptNumber=0) has a race condition: Make sets PromptNumber=0 and Status=Active at the START of Scenario 1 Stage 2, before emails 1–3 are sent. Scenario 2 could fire before email-1 is delivered.
5. In Make, a Router is a terminal point — no modules can be added after it in the same linear chain. Scenario 1 Stage 2 cannot have modules appended without a full rebuild.
6. CRITICAL CONSTRAINT confirmed: adding fields to Airtable breaks Make module field mappings across all scenarios. Do NOT change the Airtable schema.

Architecture decision locked:
Scenario 2 trigger = Custom Webhook, fired by an HTTP module in Scenario 1 Stage 2 immediately after Mailjet email-1 is sent. This guarantees email-1 precedes email-4 with no race condition and no Airtable schema changes.
