Section 2 — Make Scenario Module Maps

Each scenario maps out trigger, scenario-level filter, and module sequence. Email content (subjects + HTML) is in a separate document (item 15). For each Mailjet module here: use "Send a transactional email" → paste the relevant email HTML from item 15.

PromptNumber convention (confirm before building Scenarios 3–5, 8–9):
PromptNumber = the last prompt sent. Starts at 0. After Week 1 is sent, set to 1. After Week 2 is sent, set to 2. And so on up to 26.
Therefore: to find the next prompt to send → lookup Prompts where Week = PromptNumber + 1.
Scenario 1 Signup
Trigger: PayFast IPN webhook (Webhooks > Custom Webhook)
Scenario filter: payment_status = COMPLETE

Module sequence

  • 1
    Webhooks > Custom Webhook
    Receives PayFast IPN POST. Copy the webhook URL from Make and enter it in the PayFast merchant dashboard as the Notification URL.
  • 2
    Filter
    payment_status = COMPLETE. Discard anything else (e.g. PENDING, FAILED).
  • 3
    Airtable > Create Record [Subscribers]
    Fields to set: StorytellerFirstName, StorytellerSurname, StorytellerEmail, StoryHelperName, StoryHelperEmail, GiftGiverName, GiftGiverEmail, FamilyEmails, SubscriptionStartDate = today, Status = Active, PromptNumber = 0, LibraryToken = [see note below].
  • 4
    Airtable > Create Record [Payments]
    PayFastTransactionID = pf_payment_id, Amount = amount_gross, Date = today, Status = COMPLETE, SubscriberID = record created in step 3.
  • 5
    Mailjet > Send email-1
    TO: StorytellerEmail. Storyteller Welcome.
  • 6
    Router
    Two routes from here:
  • 6A
    Route A — Gift Giver
    Filter: GiftGiverEmail is not empty. Mailjet > Send email-2 → GiftGiverEmail.
  • 6B
    Route B — Story Helper
    Filter: StoryHelperEmail is not empty. → passes to Scenario 2 (or inline: Mailjet > Send email-3 → StoryHelperEmail). See Scenario 2 note below.
Data flow question — resolve before building: PayFast IPN carries payment data only. Subscriber form data (name, email, family list, etc.) must reach Make somehow. Two options:
Option A (simpler): Signup form on the website first POSTs to Make via a separate webhook → Make stores data in a temp Airtable record (Status = Pending) → form then redirects to PayFast, passing the Airtable record ID in PayFast's custom_str1 field → on IPN receipt, Make looks up the Pending record by custom_str1 and updates Status to Active.
Option B: Encode all subscriber data into PayFast's 5 custom_str fields (255 chars each). Feasible for short data, risky for FamilyEmails. Decide before building.
LibraryToken: This is the URL key for the subscriber's library. At v3.1 it is the SubscriberID (e.g. SUB001). Confirm the format and who generates it — either the website form passes it, or Make generates a value and stores it. A simple approach: use the Airtable record ID as the token (no separate field needed — but this changes when records are moved). Decide at build time.

Scenario 3 Week 1 Prompt
Trigger: Airtable > Watch Records [Subscribers] (new record, Status = Active) — fires when Scenario 1 creates the subscriber record
Scenario filter: Status = Active AND PromptNumber = 0

Module sequence

  • 1
    Airtable > Watch Records [Subscribers]
    Trigger on new records. Filter at scenario level: PromptNumber = 0 (i.e. no prompt sent yet).
  • 2
    Airtable > Search Records [Prompts]
    Filter: Week = 1. Retrieves: WeekName, Theme, PromptText, OtherAngles.
  • 3
    Mailjet > Send email-4
    TO: StorytellerEmail. Week 1 Prompt. Passes: WeekName, Theme, PromptText, OtherAngles, LibraryToken (for tell.html link and library link).
  • 4
    Filter + Mailjet > Send email-4
    Filter: StoryHelperEmail is not empty. Send same email-4 to StoryHelperEmail.
  • 5
    Airtable > Update Record [Subscribers]
    Set PromptNumber = 1.
tell.html link format (in email-4 and email-8):
https://24stories.co.za/tell.html?id={{LibraryToken}}&week={{PromptNumber}}&weekname={{WeekName}}&theme={{Theme}}&prompt={{PromptText}}&angles={{OtherAngles}}
Use + for spaces in URL params. Make's URL-encode function handles this.
Timing: Sending Week 1 prompt immediately on signup is recommended — it is a welcome-plus-first-prompt email (email-4 is distinct from the regular prompt email-8). No delay needed.

⚠ Prompt pace flag: This scenario runs on a fixed weekly schedule affecting ALL active subscribers simultaneously. Do NOT change the schedule cadence to handle individual pace requests. If a subscriber (e.g. a free tester) needs an accelerated schedule, use Option A or Option B from the prompt pace document — never edit the main scenario schedule. Raise this at build time.
All subscribers share the same weekly send day. Subscribers who join mid-week receive their first prompt via Scenario 3 (immediately on signup) and then join the main Monday schedule from Week 2 onwards. This means Week 2 may arrive sooner than 7 days for some subscribers. Acceptable at this volume.
Scenario 5 Day 4 Reminder
Trigger: Make > Schedule — daily (e.g. every day at 10am SAST)
Scenario filter: Status = Active AND PromptNumber >= 1

Module sequence

  • 1
    Airtable > Search Records [Subscribers]
    Filter: Status = Active AND PromptNumber >= 1 AND PromptNumber <= 26.
  • 2
    Iterator
    Loop through each subscriber.
  • 3
    Airtable > Search Records [Stories]
    Filter: SubscriberID = {{subscriber record ID}} AND PromptNumber = {{subscriber's PromptNumber}}. Checks whether a story exists for the current week.
  • 4
    Filter — no story yet
    Filter: Stories record count = 0 (no story submitted for current prompt week). AND today = [prompt send date + 3 days] — see date logic note below.
  • 5
    Mailjet > Send email-5
    TO: StorytellerEmail. Day 4 Reminder.
  • 6
    Filter + Mailjet > Send email-5
    Filter: StoryHelperEmail is not empty. Send same email-5 to StoryHelperEmail.
Date logic — resolve at build time: To calculate "day 4 since prompt was sent", Make needs to know when the prompt was sent. Options:
Option A: Add a LastPromptSentDate field to Subscribers table. Scenario 4 writes today's date each time it sends. Scenario 5 compares today to LastPromptSentDate + 3.
Option B (no extra field): Derive the send date: all subscribers receive prompts on the same day of week. Make can calculate: most recent [weekday name] at or before today = last prompt date. Add 3 to get day 4.
Option A is simpler and more reliable. Recommend adding LastPromptSentDate to Subscribers table.
Send reminder only once. Add a check to avoid double-sending: if a reminder was already sent for this week, skip. Options: (a) track in a ReminderSentWeek field on Subscribers, (b) rely on the fact that the reminder fires on a specific day only. Option B is sufficient at this scale.

Scenario 10 Daily Book Production Alert — Tamara
Trigger: Make > Schedule — daily at 8am SAST
Scenario filter: BookFormCompleted is not empty AND BookSentToPrintDate is empty

Alert thresholds

Yellow = 42+ days since BookFormCompleted. Red = 49+ days since BookFormCompleted.

Module sequence

  • 1
    Airtable > Search Records [Subscribers]
    Filter: BookFormCompleted is not empty AND BookSentToPrintDate is empty. Returns all books currently in production.
  • 2
    Filter — any overdue books?
    Filter: at least one record has BookFormCompleted date that is 42 or more days ago. If none qualify, scenario ends silently — no email sent.
  • 3
    Tools > Set Variables
    For each subscriber in production: calculate days elapsed since BookFormCompleted. Classify as Yellow (42–48 days) or Red (49+ days). Build the alert email body as a formatted list.
  • 4
    Mailjet > Send alert
    TO: hello@24stories.co.za (Tamara). Subject: "Book production alert — action required". Body: table of overdue books — subscriber name, date BookFormCompleted was set, days elapsed, BookProductionStatus (current stage). Yellow and Red items distinguished clearly in the body.
Quiet days: If no subscriber meets the 42-day threshold, the scenario must end without sending any email. Implement by adding a filter at step 2: only continue if at least one overdue record exists. This prevents daily noise to Tamara.
Building the alert body in Make: Use a Text Aggregator module to concatenate per-subscriber rows before passing to Mailjet. Each row: subscriber name | date pressed Complete | days elapsed | current stage.

Scenario 13 Pause Expiry Reminder
Trigger: Make > Schedule — daily at 9am SAST
Scenario filter: Status = Paused AND PauseStartDate is not empty

Module sequence

  • 1
    Airtable > Search Records [Subscribers]
    Filter: Status = Paused AND PauseStartDate is not empty.
  • 2
    Iterator
    Loop through each paused subscriber.
  • 3
    Tools > Set Variables
    Calculate days since PauseStartDate. Calculate expiry date = PauseStartDate + 365 days.
  • 4
    Filter
    days since PauseStartDate >= 335 AND <= 365 (i.e. within 30 days of 12-month expiry). Sends one reminder in the final month of the pause window.
  • 5
    Mailjet > Send reminder
    TO: StorytellerEmail. Body: "Your pause period is coming to an end. Please email hello@24stories.co.za before [expiry date] to resume your subscription." Not one of the 16 numbered emails — write inline in Make or as a simple Mailjet template.
After 365 days — no auto-cancel. The architecture does not specify automatic cancellation. At launch, Tamara handles this manually: if a subscriber does not respond to the reminder, Tamara updates Status to Cancelled in Airtable at her discretion. Do not build auto-cancel logic at launch.
Pause management — Tamara only. Subscribers request a pause by emailing hello@24stories.co.za. Tamara: (1) updates Status to Paused in Airtable, (2) sets PauseStartDate, (3) sends email-15 (Pause Confirmation) manually. Make scenarios that check Status = Active will automatically skip paused subscribers. No additional pause logic needed in other scenarios.
