Section 1 — Scenario Flag Decisions

Scenario 1 Signup — data flow and LibraryToken

Flag 1A — How subscriber data flows from form to Airtable

PayFast IPN carries payment data only. Subscriber name, emails, family list etc. must reach Make separately.

Decision: Two-stage flow (Option A).
Stage 1: Checkout form POSTs subscriber data to a Make webhook → Make creates Subscribers record with Status = Pending.
Stage 2: PayFast IPN fires to Scenario 1 webhook with payment_status = COMPLETE and custom_str1 = the Pending record's Airtable record ID → Make looks up and updates the record: Status = Active, SubscriptionStartDate = today, PromptNumber = 0, LibraryToken = record ID.
Stage 1 is a small separate Make scenario — see Section 2. Stage 2 is Scenario 1 proper. Emails 1–3 fire only after Stage 2 completes. The Pending record is ignored by all other scheduled scenarios (they filter Status = Active).

Flag 1B — LibraryToken format

What value goes into LibraryToken and who generates it?

Decision: Use the Airtable record ID.
Stage 2 sets LibraryToken = custom_str1 (which is the record ID passed from Stage 1 via PayFast). Library URL format: library.html?id={{LibraryToken}}. Airtable record IDs do not change during normal use.

Flag 1C — Story Helper Welcome (Scenario 2)

Implement as separate scenario or as Route B within Scenario 1?

Decision: Route B within Scenario 1.
After sending email-1, add a Router. Route A: GiftGiverEmail not empty → send email-2. Route B: StoryHelperEmail not empty → send email-3. No separate Make scenario needed. Scenario 2 is listed in the architecture for clarity but is not a separate build item.
Scenario 3 Week 1 Prompt — timing

Flag — When does Week 1 prompt send?

Send immediately on signup or on the next scheduled Monday?

Decision: Immediately on signup.
Scenario 3 is triggered by Airtable Watch Records detecting the new Active subscriber. It fires automatically, no delay. After sending, sets PromptNumber = 1 and LastPromptSentDate = today.
Week 2 will then arrive on the next Monday send, which may be fewer than 7 days if signup is mid-week. Acceptable at this volume.
Scenario 4 Regular Prompt Delivery — prompt pace

Flag — How to handle accelerated subscribers (free testers)

Weekly schedule affects all subscribers simultaneously. Cannot change cadence for one subscriber without affecting all.

Decision: Build Option B — separate "Send Next Prompt — Manual" scenario.
A webhook-triggered scenario that accepts a SubscriberID, looks up that subscriber's PromptNumber, fetches the next prompt, sends email-8, and increments PromptNumber. Tamara fires it manually for specific subscribers only. Main weekly scenario untouched. Build this alongside Scenario 4 — see Section 2.
After sending, Scenario 4 always sets LastPromptSentDate = today on the subscriber record. The manual scenario does the same.
Scenario 5 Day 4 Reminder — date logic and double-send guard

Flag 5A — How to know when the last prompt was sent

Scenario 5 runs daily and needs to know if today is exactly day 4 after the last prompt send.

Decision: Use LastPromptSentDate field (Option A).
New Date field added to Subscribers table. Scenarios 3, 4, and the manual prompt scenario all write today's date to this field after sending. Scenario 5 calculates: today - LastPromptSentDate = 3 days (day 4 is 3 days after send date). Filter on this before sending email-5.

Flag 5B — Prevent double-sending the reminder

Scenario 5 runs daily. Could send the reminder more than once if not guarded.

Decision: Option B — rely on day-specific calculation only. No extra field.
The filter today - LastPromptSentDate = exactly 3 means the scenario only acts on day 4. On day 5 and beyond, the condition fails. At this volume, this is a sufficient guard. No ReminderSentWeek field needed.
Scenario 6 Story Edited — double-send guard and FamilyEmails delimiter

Flag 6A — Prevent double-sending when Tamara edits a typo in EditedText

Airtable Watch re-triggers on any update to the Stories record, including typo fixes after emails have already been sent.

Decision: Add EmailsSent checkbox to Stories table.
Scenario 6 filter: EditedText not empty AND EmailsSent is not checked. After email-6 and email-7 send successfully, Make sets EmailsSent = true. All subsequent edits to that Stories record are ignored.

Flag 6B — FamilyEmails delimiter

Split Text module needs to know the separator character.

Decision: Newline (\n) — one email address per line.
This is the format the checkout form will use (confirmed). In Make, use the Split Text module with separator = \n. The resulting array feeds the Iterator for family email sends.
Scenario 7 Resend Library Link — email format

Flag — Use inline HTML or Mailjet template?

The "here is your library link" email is not one of the 16 numbered emails.

Decision: Write inline in Make.
Simple one-paragraph email. Write the HTML directly in the Mailjet module — no template needed. Subject: "Your 24 Stories library link". Body: one sentence + the library URL. Signed: "With warmth, The 24 Stories Team."
The "not found" Route B email is also inline. One sentence: "We could not find an account linked to this email address. Please contact hello@24stories.co.za."
Scenario 8 Book Onboarding — date field for reminders

Flag — How does Scenario 9 know when email-9 was sent?

Scenario 9 needs the exact date email-9 was sent to calculate Day 3, 7, and 14 offsets.

Decision: Add BookOnboardingEmailDate field (Date) to Subscribers.
Scenario 8 writes today's date to this field after sending email-9. Scenario 9 reads it to calculate days elapsed. Cleaner and more reliable than deriving from the weekly schedule.
Scenario 9 Book Onboarding Reminders — escalation limit

Flag — What happens after Day 14?

Decision: No further automated reminders. Tamara follows up manually.
After email-11 (Day 14), the scenario takes no further automated action for that subscriber. Tamara handles individually. No additional Make logic needed.
Scenario 10 Daily Book Production Alert — quiet days

Flag — Suppress alert when no books are overdue

Decision: Filter after search — stop if no overdue records.
After searching Subscribers (BookFormCompleted not empty AND BookSentToPrintDate empty), add a filter: at least one record has BookFormCompleted 42+ days ago. If none qualify, the scenario ends silently — no email to Tamara. This prevents daily noise.
Use a Text Aggregator to build the alert email body: one row per overdue subscriber — name, date pressed Complete, days elapsed, current BookProductionStatus. Feed this aggregated text into the Mailjet module body.
Scenario 11 Book Sent to Print — double-send guard

Flag — Prevent re-sending email-12 if Tamara corrects the date

If Tamara sets BookSentToPrintDate, email-12 fires. If she then corrects the date (typo), the Watch triggers again.

Decision: Add BookDispatchEmailSent checkbox to Subscribers.
Scenario 11 filter: BookSentToPrintDate not empty AND BookDispatchEmailSent is not checked. After email-12 sends, Make sets BookDispatchEmailSent = true. Date corrections after that are ignored.
Gift Giver copy of email-12: Tamara sends manually from hello@24stories.co.za if a Gift Giver exists. Not automated at launch.
Scenario 12 Extra Copies — webhook and intermediate step

Flag 12A — Separate webhook URL or same as Scenario 1?

Decision: Separate webhook URL.
Scenario 12 uses its own Make webhook URL, distinct from Scenario 1. PayFast distinguishes by URL. No need to filter by item_name or custom_str flags.

Flag 12B — Quantity tracking

Decision: Track via Payments table only.
Each extra copies transaction creates one Payments record. Quantity = Amount ÷ 1200. No ExtraCopiesOrdered field needed.

Flag 12C — Intermediate step (library → Make → PayFast link → subscriber pays)

The library needs to initiate the extra copies order. Make then needs to get a PayFast payment link to the subscriber. Dynamic PayFast link generation in Make is complex.

Decision: Manual intermediate step at launch.
Library "Order extra copies" button fires a webhook to Make (separate from the 4 library webhooks — see Section 2). Make sends a notification email to Tamara: "Subscriber X has requested N extra copies (R[N×1200]). Please send them a PayFast payment link." Tamara sends the link manually. Subscriber pays → IPN → Scenario 12 → email-14. Fully automating the link generation can be added later without touching any other scenario.
Library webhook gap: The extra copies request webhook is a 5th library webhook not listed in the original library_config_checklist. Build it when building Scenario 12. Add the URL to library.html at that point.
Scenario 13 Pause Expiry Reminder — auto-cancel

Flag — Auto-cancel after 12 months?

Decision: No auto-cancel. Tamara handles manually.
After 365 days, if subscriber does not respond to the reminder, Tamara sets Status = Cancelled in Airtable at her discretion. Make takes no automated action beyond sending the reminder email.

Section 2 — Additional Make Scenarios Beyond the 13

The 13 scenarios cover email automation. The following additional Make scenarios are required for the system to function. Build these in Make alongside the 13 — they are simple (2–4 modules each).

Additional scenarios to build

  • Scenario 1 — Stage 1 (pre-payment): Webhook receives checkout form data → creates Subscribers record with Status = Pending. Passes record ID to PayFast via redirect. 3 modules: webhook, create Airtable record, update record (set LibraryToken = record ID).
  • Library webhook A — Story photo: Webhook receives { subscriberId, week, photoUrl } → updates Stories.StoryImageURL for matching record. 3 modules.
  • Library webhook B — Story caption: Webhook receives { subscriberId, week, caption } → updates Stories.StoryImageCaption. 3 modules.
  • Library webhook C — Book photo: Webhook receives { subscriberId, fieldType, photoUrl } → if fieldType = "portrait", updates Subscribers.PortraitPhotoURL; if "cover", updates Subscribers.CoverPhotoURL. 3–4 modules with router.
  • Library webhook D — Book text: Webhook receives { subscriberId, fieldType, value } → routes to correct Subscribers field: DedicationText / DeliveryAddress / BookTitle / BookFormCompleted (when fieldType = "bookComplete", sets BookFormCompleted = today). 4–5 modules with router.
  • Library webhook E — Extra copies request: Webhook receives { subscriberId, quantity } → emails Tamara at hello@24stories.co.za with subscriber name and amount. 3 modules. (Tamara then sends PayFast link manually.)
  • Manual prompt scenario — "Send Next Prompt": Webhook receives { subscriberId } → looks up subscriber → fetches Prompts record where Week = PromptNumber + 1 → sends email-8 → increments PromptNumber → sets LastPromptSentDate. 6 modules. Tamara fires manually for accelerated testers.
Total Make scenarios to build: 20 (13 main + Stage 1 pre-payment + 5 library webhooks + 1 manual prompt). Library webhooks A–D are all simple — webhook → Airtable update. Allow 2–3 hours for all 20.
BookFormCompleted is set via Library webhook D (fieldType = "bookComplete"), not a separate webhook. The "Mark as Complete" button in library.html fires webhook D with fieldType = "bookComplete" and value = today's date. Make sets BookFormCompleted = that date. This triggers Scenario 10 to start watching that subscriber.

Section 3 — Build Order for Make

Build in this order. Each scenario is testable before moving to the next. Test each one with manually sent webhook data before proceeding.

  1. Scenario 1 — Stage 1 (pre-payment webhook → create Pending record)
  2. Scenario 1 — Stage 2 (PayFast IPN → activate record → emails 1, 2, 3)
  3. Scenario 3 — Week 1 Prompt (Airtable Watch → send email-4 → set PromptNumber = 1, LastPromptSentDate)
  4. Scenario 4 — Regular Prompt Delivery Weeks 2–26 (scheduled weekly → loop → send email-8 → increment PromptNumber, update LastPromptSentDate)
  5. Manual Prompt scenario — webhook-triggered single-subscriber prompt send
  6. Scenario 5 — Day 4 Reminder (daily schedule → check LastPromptSentDate → send email-5)
  7. Scenario 6 — Story Edited (Airtable Watch → send email-6 → send email-7 to family → set EmailsSent)
  8. Scenario 7 — Resend Library Link (webhook → lookup → send link or not-found email)
  9. Library webhooks A–E — all five simple webhook → Airtable update scenarios
  10. Scenario 8 — Book Onboarding Week 26 (routed from Scenario 4 → send email-9 → set BookOnboardingEmailDate)
  11. Scenario 9 — Book Onboarding Reminders (daily schedule → check BookOnboardingEmailDate → send email-10 or email-11)
  12. Scenario 10 — Daily Book Production Alert (daily schedule → check overdue books → email Tamara)
  13. Scenario 11 — Book Sent to Print (Airtable Watch → send email-12 → set BookDispatchEmailSent)
  14. Scenario 12 — Extra Copies (PayFast IPN → Payments record → send email-14)
  15. Scenario 13 — Pause Expiry Reminder (daily schedule → check PauseStartDate → send reminder)
Once all scenarios are built and tested: Update library.html with the 5 webhook URLs (A–E). Replace MAKE_WEBHOOK_URL_PLACEHOLDER in index.html with the Scenario 7 webhook URL. Both are in the library_config_checklist.
